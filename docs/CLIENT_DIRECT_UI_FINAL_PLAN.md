## 0. 总原则

当前不要重新推翻方向：

1. 主路线仍然是 **X5Game.exe 客户端直登**。
2. 不要改成 Chrome / Edge / Playwright 普通浏览器登录。
3. 不要使用 Playwright `connect_over_cdp`。
4. 不要做并发。
5. 不要破坏原 OCR / 通行证兜底流程。
6. 不要破坏方式二：账号密码 + 通行证上号。
7. 不要全局扫描并自动接管所有 X5Game.exe。
8. 客户端直登相关操作只能围绕 GUI 当前选中的 `batch_id` / 当前批次绑定里的 `pid`、`hwnd`、`cdp_port`。
9. 日志和 GUI 都不能显示完整 `token`、`sign`、`cookie`、`IMEI`、`uid`、`session`、`openid`、完整 `login.php URL`。
10. 不要 `reset`，不要 `checkout`，不要清空 untracked 文件，不要删除已有源码文件。
11. 本次重点是 UI 架构和客户端直登流程收尾，不是重构整个项目。

## 2. 整体 UI 结构

现在界面有点混乱：窗口管理、客户端直登批次、前台辅助、旧按钮混在一起。

请改成以下结构：

```text
窗口管理
读取收藏夹 / 账号配置
工作模式：[客户端直登模式] [前台辅助模式]
当前模式运行区：
  - 如果是客户端直登模式，只显示客户端直登批次区域
  - 如果是前台辅助模式，只显示旧流程 / 方式一 / 方式二区域
底部状态栏：
  - 状态
  - 当前模式
  - 当前批次
  - 最近消息
  - 展开日志 / 复制日志
```

要求：

1. 客户端直登区域和前台辅助区域不能同时显示。
2. 不要把两套运行区左右并排同时放出来。
3. 日志区域默认隐藏，不要改成常驻大日志区。
4. 保留“展开日志 / 收起日志 / 复制日志 / 清空日志”入口。
5. 正常状态下界面优先显示窗口管理、账号来源、工作模式和当前模式运行区。

## 3. 工作模式改成顶层切换

当前“模式”下拉框不应该继续放在“层级 / 账号 / 并发 / 重试次数”那一行。

原因：

> “模式”不是普通参数，而是决定整个运行区域显示逻辑的顶层入口。

修复要求：

1. 把“模式”改成“工作模式”。
2. 放在读取收藏夹 / 账号配置区域下面，当前模式运行区上面。
3. 工作模式只保留：
   - 客户端直登模式
   - 前台辅助模式
4. 默认模式必须是：
   - 客户端直登模式
5. 模式下拉框或模式选择按钮里不再显示：
   - 后台登录模式（实验）
   - 后台模式
6. 注意实际旧字符串可能是“后台登录模式（实验）”，请按真实字符串处理。
7. 切换工作模式时，统一调用 `update_mode_ui` / `refresh_mode_controls` / `on_mode_changed` 之类方法控制显示隐藏，不要到处零散判断。

## 8. 客户端直登数量来源

当前容易混淆：

```text
窗口管理里的“打开数量”
和
客户端直登里的“本批数量”
```

这两个不是一回事。

客户端直登模式下：

1. “准备客户端 / 一键准备并登录 / 追加准备”的数量必须来自客户端直登账号筛选结果，也就是“本批数量”。
2. 本批数量根据当前账号筛选范围计算。
3. 端口范围根据本批数量计算：

```text
起始端口 ~ 起始端口 + 本批数量 - 1
```

4. 窗口管理区域里的“打开数量”属于旧批量启动窗口参数，不应该影响客户端直登准备数量。
5. 如果用户想准备 9 个客户端，应通过账号范围 / 层级 / 筛选控制为 9 个，而不是修改窗口管理里的打开数量。
6. 客户端直登模式下隐藏窗口管理里的“打开数量”，避免出现“打开数量=9，本批数量=31”的误解。

## 9. 批次持久化恢复与失效批次自动清理

批次记录保存在本地：

```text
debug_client_direct/client_direct_sessions.json
```

上号器关闭后再打开：

1. 如果 X5Game.exe 还活着，应该能通过 sessions 恢复批次。
2. 如果游戏窗口后来全部关闭，旧批次不应该一直留在下拉框里。

新增重要规则：

1. 上号器启动时读取 `client_direct_sessions.json`。
2. 启动后自动刷新所有批次状态：
   - pid 是否存在
   - pid 是否仍为 X5Game.exe
   - cdp_port 是否可访问
   - hwnd 是否有效
3. 如果批次里仍有存活 X5Game.exe：
   - 保留批次
   - 显示在当前批次下拉框
   - 允许修复、排列、关闭、继续登录
4. 如果批次存活数量 = 0：
   - 默认自动清理这个失效批次
   - 只删除 sessions 里的 batch 记录
   - 不关闭任何 X5Game.exe
   - 不删除 `client_direct_sessions.json` 文件本身
5. 如果 pid 还存在，但 cdp_port 不通或 hwnd 无效：
   - 不自动删除
   - 标记为 CDP不可用 / 窗口失效
   - 允许用户点“修复本批窗口”
6. 清理后刷新批次下拉框、绑定列表和批次统计。
7. 日志打印：

```text
[批次恢复] 保留存活批次 x 个，自动清理失效批次 y 个。
```

8. 不允许全局扫描并自动接管未知 X5Game.exe。

## 10. 新增删除当前批次 / 清理失效批次

当前批次下拉框旁边新增：

- 重命名批次
- 删除当前批次
- 清理失效批次

### 10.1 删除当前批次

要求：

1. 只删除 GUI 当前选中的 `batch_id`。
2. 从 `client_direct_sessions.json` 的 `batches` 中移除该 batch。
3. 如果删除的是 `active_batch_id`：
   - 自动切换到剩余第一个批次。
   - 如果没有剩余批次，则 `active_batch_id` 置空。
4. 删除后刷新：
   - 批次下拉框
   - 绑定列表
   - 批次统计
5. 删除批次默认只删除绑定记录，不关闭 X5Game.exe。
6. 如果当前批次存活数量 > 0，必须弹窗强确认：

```text
当前批次仍有存活客户端 xx 个。
删除批次只会删除绑定记录，不会关闭客户端。
如需关闭客户端，请先点击“关闭本批客户端”。
是否仍然删除批次记录？
```

7. 不允许删除其他未选中批次。
8. 不允许全局扫描或接管 X5Game.exe。

### 10.2 清理失效批次

要求：

1. 只清理存活数量=0 的批次。
2. 判断前先刷新 sessions 状态。
3. `pid_missing`、`closed_by_tool`、`hwnd_invalid`、`cdp_unavailable` 且无存活窗口的批次可以清理。
4. 有任意存活 X5Game.exe 的批次不能清理。
5. 清理前弹窗显示将要清理的批次数量和批次名称。
6. 清理后刷新批次下拉框、绑定列表、批次统计。
7. 不关闭任何 X5Game.exe。
8. 不删除 `client_direct_sessions.json` 文件本身，只更新里面的 `batches`。

## 11. 一键准备并登录弹窗逻辑

一键准备并登录是快速入口，正常情况下不需要弹普通确认框。

点击“一键准备并登录”后直接执行：

```text
准备客户端
→ 自动排列本批客户端
→ 如果勾选排列后自动编号标题，则自动重命名窗口
→ 执行客户端登录
→ 如果勾选自动进入游戏，则自动进入游戏
```

### 11.1 不需要弹窗的情况

1. 正常开始一键准备并登录，不弹确认。
2. 端口范围不可用，但程序能找到下一段连续可用端口，也不弹确认，直接自动更新起始端口并继续执行。

例如：

```text
用户填写起始端口 9222，本批数量 31。
9222~9230 被占用。
程序找到 9231~9261 可用。
则自动把起始端口更新为 9231，并继续准备。
```

但是日志必须打印：

```text
[端口预检] 原端口 9222~9252 不可用，系统占用=9222~9230，自动改用推荐端口 9231~9261。
```

端口推荐仍必须满足：

1. 找连续可用端口区间。
2. 长度必须等于本批数量。
3. 不允许边开边跳过零散端口。
4. 不允许静默使用不连续端口。
5. 不允许接管其他 X5Game.exe。
6. 只避开真实 LISTENING 端口和存活 X5Game 批次绑定端口。

### 11.2 必须弹窗的情况

真正失败时必须弹窗，并告知原因，例如：

- X5Game.exe 路径不存在
- URL 不是完整直登 URL
- 启动 X5Game.exe 失败
- CDP 端口不可访问
- hwnd 获取失败
- Page.navigate 失败
- importServer 失败
- gameNotice 失败
- serverMobile 失败
- canvas 未出现
- 自动进入游戏失败

弹窗要告诉用户：

1. 哪个账号失败。
2. 失败在哪一步。
3. 失败原因是什么。

### 11.3 部分失败

如果准备 31 个，成功 28 个，失败 3 个，必须弹窗：

```text
成功：28
失败：3

失败账号：
- 账号12：CDP 端口不可访问
- 账号18：URL 不完整
- 账号27：hwnd 获取失败

是否继续排列并登录成功的 28 个？
```

用户确认后，只处理成功 bindings。  
用户取消后，停止后续排列和登录。

### 11.4 破坏性操作仍然必须确认

以下操作必须弹确认：

- 关闭本批客户端
- 清空本批绑定
- 删除当前批次
- 清理失效批次

## 12. 一键准备并登录必须真正进入游戏

实测发现：

一键准备并登录后，X5Game.exe 已经打开并直登到游戏入口阶段，但没有真正进入游戏。

表现：

1. GUI 状态是“客户端已就绪”，不是“客户端登录成功”。
2. 有的窗口停在“进入游戏”按钮页面。
3. 有的窗口弹出公告窗口。
4. “自动进入游戏”已经勾选，但流程没有继续进入游戏。

修复要求：

1. 检查“一键准备并登录”是否正确读取 GUI 的“自动进入游戏”勾选状态。
2. 如果 `auto_enter_game=true`，执行客户端登录时不能只停在 `importServer / gameNotice` 阶段。
3. 必须继续执行已有客户端直登自动进入游戏逻辑：
   - 处理 gameNotice / 公告弹窗
   - 关闭公告或点击公告外区域
   - 触发“进入游戏”
   - 等待 serverMobile success
   - 等待 GameMain/main.js loaded
   - 等待 canvas visible
   - 最终状态更新为 `login_success / 客户端登录成功`
4. 如果 `auto_enter_game=false`，才允许停在“客户端已就绪”。
5. “一键准备并登录”和“执行客户端登录”两个入口必须共用同一套 `auto_enter_game` 逻辑。
6. 日志需要明确打印：
   - `auto_enter_game=true/false`
   - 当前停在哪一步：`notice / enter_button / serverMobile / canvas`

## 13. 追加准备

追加准备保留。

含义：

> 在当前批次已经有一部分客户端的情况下，继续往这个批次里追加打开新的 X5Game.exe，不清空旧绑定、不关闭旧窗口。

适用场景：

1. 分批打开，例如先准备 10 个，再追加 10 个，再追加 11 个。
2. 31 个里失败了几个，只追加失败账号。
3. 先开 2 个测试，没问题再追加剩下的。

要求：

1. “追加准备”只在客户端直登模式显示。
2. 追加准备必须只追加到 GUI 当前选中的 `batch_id`。
3. 追加准备不能清空旧绑定。
4. 追加准备不能关闭旧 X5Game.exe。
5. 追加准备不能影响其他批次。
6. 追加准备正常情况下可以不弹普通确认。
7. 失败时必须弹窗说明原因。
8. 端口可自动推荐时不弹确认，只写日志。

## 14. 端口占用判断继续保持已修复逻辑

不要回退端口判断逻辑。

当前正确规则：

1. `is_tcp_port_available` 以真实 LISTENING / connectable 为准。
2. 不要再改回 bind() 判断方式。
3. 准备前刷新 sessions 状态。
4. 失效旧 binding 不阻止端口准备。
5. `pid_missing`、`closed_by_tool`、`hwnd_invalid`、`cdp_unavailable` 的旧绑定端口不算占用。
6. 只有两类端口阻止准备：
   - 系统真实 LISTENING 端口
   - sessions 中 pid 仍存在且进程仍为 X5Game.exe 的存活绑定端口
7. 弹窗或日志区分：
   - 系统真实占用端口
   - 存活批次绑定端口
8. 端口推荐必须找连续区间。
9. 不要边开边跳过零散端口。

## 15. 当前批次操作原则

所有本批操作必须使用 GUI 当前选中的 `batch_id`，包括：

- 准备客户端
- 一键准备并登录
- 追加准备
- 排列本批客户端
- 执行客户端登录
- 修复本批窗口
- 清空本批绑定
- 关闭本批客户端
- 删除当前批次
- 清理失效批次

要求：

1. 切换批次下拉框时必须同步 `active_batch_id`。
2. 切换批次后刷新绑定列表和批次统计。
3. 不允许根据虚拟桌面自动切换批次。
4. `virtual_desktop_note` 只能作为备注，不能作为技术判断依据。
5. 不允许根据标题全局接管窗口。
6. 不允许全局扫描所有 X5Game.exe 并自动接管。

## 19. 测试要求

修复后补充 / 更新测试：

1. 工作模式只包含：
   - 客户端直登模式
   - 前台辅助模式
2. 不包含：
   - 后台登录模式（实验）
   - 后台模式
3. 默认模式是客户端直登模式。
4. 客户端直登模式下：
   - 客户端直登批次区域可见。
   - 前台辅助运行区不可见。
   - 单账号运行 / 当前层串行 / 全部串行不可见。
   - 方式一 / 方式二入口不可见。
   - 窗口管理旧启动项打开数量 / 启动间隔 / 批量启动窗口不可见。
   - 窗口布局参数仍可见。
5. 前台辅助模式下：
   - 前台辅助运行区可见。
   - 客户端直登批次区域不可见。
   - 一键准备并登录 / 追加准备 / 当前批次等不可见。
   - 方式一 / 方式二可见。
6. 读取收藏夹 / 账号列表在两种模式下都可见。
7. 客户端直登本批数量来自账号筛选结果，不来自窗口管理打开数量。
8. 启动恢复：
   - 有存活 X5Game.exe 的批次保留。
   - 存活=0 的失效批次自动清理。
   - pid 仍存在但 CDP 不通 / hwnd 无效的批次不自动删除。
9. 删除当前批次：
   - 只删除选中的 batch。
   - 删除 active batch 后自动切换 active_batch_id。
   - 删除最后一个 batch 后 active_batch_id 置空。
   - 存活数量 > 0 时必须强确认。
10. 清理失效批次：
   - 只删除存活=0 的批次。
   - 存活>0 的批次不会被清理。
11. 一键准备并登录：
   - 正常开始不弹确认。
   - 推荐端口自动切换不弹确认。
   - 失败时弹窗显示原因。
   - 部分失败时弹窗询问是否继续成功项。
12. `auto_enter_game=true`：
   - 不能停在 `ready_no_enter`。
   - 必须继续尝试进入游戏并最终更新为 `login_success / 客户端登录成功`。
13. `auto_enter_game=false`：
   - 允许停在客户端已就绪。
14. 所有本批操作只作用当前 `batch_id`。
15. 排列后重命名只作用当前 `batch_id`。
16. URL 脱敏显示测试继续通过。
17. 日志脱敏测试继续通过。
18. 方式二相关控件和配置在前台辅助模式下仍可见，不被删除。
