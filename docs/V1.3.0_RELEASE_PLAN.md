# 二、P0：用户配置与批次数据持久化

## 2.1 当前问题

当前用户配置可能保存在：

- 程序目录
- `dist`
- `_internal`
- `debug_client_direct`

重新打包或客户使用全新 zip 包时，配置会丢失，导致：

- 游戏路径丢失
- 窗口布局丢失
- 账号来源路径丢失
- 端口配置丢失
- 加速器配置丢失
- 批次记录丢失

客户更新方式是：

> 每次下载一个全新的 zip 包，解压到一个全新的目录，然后直接打开新 EXE 使用。

例如：

```text
斗罗大陆H5上号器-v1.2.0\
斗罗大陆H5上号器-v1.3.0\
斗罗大陆H5上号器-v1.4.0\
```

这些是不同目录，但用户配置必须保留。

所以用户真实配置不能保存在程序目录。  
不能保存在 `_internal`。  
不能保存在 `dist`。  
不能只保存在便携 `data` 目录。

必须默认保存到稳定的 Windows 用户数据目录。

---

## 2.2 默认用户数据目录

默认使用：

```text
%APPDATA%\DouluoH5Launcher\
```

结构：

```text
%APPDATA%\DouluoH5Launcher\
  automation_settings.json
  client_direct_sessions.json
  logs\
  backups\
```

要求：

1. EXE 放在哪个新解压目录都无所谓。
2. 程序启动后都读取同一个 `%APPDATA%\DouluoH5Launcher`。
3. 客户每次下载全新 zip、解压到新文件夹，也能继续读取旧配置。
4. 本机重新打包或换目录运行，也不会丢游戏路径和批次。
5. 客户自己的配置保存在客户自己的 Windows 用户目录，不会带开发机配置。

---

## 2.3 环境变量覆盖

支持环境变量：

```text
H5_LAUNCHER_DATA_DIR
```

如果设置了，就优先使用这个目录。

如果没设置，就使用：

```text
%APPDATA%\DouluoH5Launcher\
```

示例：

```text
H5_LAUNCHER_DATA_DIR=D:\Ai\codex\上号器\dev_user_data
```

用于开发调试。

---

## 2.4 启动初始化规则

程序启动时：

1. 确定 `user_data_dir`。
2. 如果目录不存在，自动创建。
3. 如果 `user_data_dir/automation_settings.json` 不存在：
   - 从 `automation_settings.template.json` 生成。
4. 如果 `user_data_dir/client_direct_sessions.json` 不存在：
   - 创建空 sessions。
5. logs 写到 `user_data_dir/logs`。
6. backups 写到 `user_data_dir/backups`。

不能再把真实用户配置写到：

- `_internal/automation_settings.json`
- `dist/Launcher/_internal/automation_settings.json`
- 程序目录 `automation_settings.json`
- `debug_client_direct/client_direct_sessions.json`

这些旧路径只能作为迁移来源，不能继续作为正式运行路径。

## 2.5 旧数据迁移

为了兼容当前旧版本，如果 `%APPDATA%\DouluoH5Launcher` 里还没有配置，就尝试从旧路径迁移。

`automation_settings.json` 迁移来源优先级：

1. EXE 同级目录 `automation_settings.json`
2. EXE 同级目录 `_internal/automation_settings.json`
3. 当前工作目录 `automation_settings.json`
4. 当前工作目录 `dist/Launcher/_internal/automation_settings.json`

`client_direct_sessions.json` 迁移来源优先级：

1. EXE 同级目录 `client_direct_sessions.json`
2. EXE 同级目录 `debug_client_direct/client_direct_sessions.json`
3. EXE 同级目录 `_internal/debug_client_direct/client_direct_sessions.json`
4. 当前工作目录 `debug_client_direct/client_direct_sessions.json`
5. 当前工作目录 `dist/Launcher/debug_client_direct/client_direct_sessions.json`
6. 当前工作目录 `dist/Launcher/_internal/debug_client_direct/client_direct_sessions.json`

迁移规则：

1. 只在 `user_data_dir` 里没有对应文件时迁移。
2. 迁移是 copy，不删除旧文件。
3. 迁移成功后，正式读写都走 `user_data_dir`。
4. 不继续写旧路径。
5. 迁移前先在 `user_data_dir/backups/` 里创建备份目录。
6. 迁移日志提示：

```text

[数据迁移] 已迁移 client_direct_sessions.json 到用户数据目录
```

# 三、P1：修复本批窗口异常恢复增强

## 3.1 背景

实际使用中，X5Game 窗口可能会出现白屏、卡死、进程残留、CDP 端口残留、hwnd 残留、用户强制关闭窗口、pid 已存在但不是正常 `X5Game.exe` 等情况。

这种情况会经常发生，尤其是大量窗口长期运行时。

当前观察到的问题：

1. 某个窗口白屏 / 卡死后被强制关闭。
2. 点击“修复本批窗口”。
3. 个别账号可能出现 `pid_not_x5game`。
4. 部分已经登录成功的账号状态可能被改成 `restored`。
5. `restored` 作为修复动作结果可以存在，但不应该覆盖账号业务状态。

这不是打包问题，而是批次恢复 / 修复窗口绑定逻辑需要增强。

## 3.2 修复目标

“修复本批窗口”只允许修复窗口绑定信息，不能覆盖账号业务状态。

允许修复：

- `pid`
- `hwnd`
- `cdp_port`
- 窗口标题
- 窗口位置
- CDP 可用性
- 进程存活状态

不允许覆盖：

- 客户端登录成功
- 已进入游戏
- 客户端已就绪
- `login_success`
- `game_entered`
- `ready`
- `running`
- `login_failed`
- `enter_game_failed`

## 3.3 状态保留规则

修复开始前，对每个 binding 保存：

- `old_status`
- `old_display_status`
- `old_error_message`
- `old_login_state`
- `old_business_state`

修复成功后：

1. 如果原状态是业务成功状态，例如客户端登录成功、已进入游戏、`login_success`、`game_entered`、`ready`、`running`，则修复后必须保持原业务状态。
2. 如果原状态是失败状态，例如 `login_failed`、`enter_game_failed`、`cdp_unavailable`，修复窗口成功后不要直接改成 `restored`。可以只清理窗口绑定错误，但业务失败状态是否清理要按原逻辑判断。
3. `restored` 只能作为修复动作结果，不应作为账号列表里的最终业务状态。

可以新增独立字段，例如：

- `repair_status=restored`
- `window_status=restored`

但不要覆盖：

- `status`
- `display_status`
- `login_status`

## 3.4 白屏 / 卡死 / 强制关闭后的异常绑定识别

如果检测到 `pid_not_x5game`：

1. 说明当前 binding 的 pid 不是 `X5Game.exe`。
2. 不应视为修复成功。
3. 不应计入正常存活。
4. UI 状态可以显示 `pid_not_x5game` 或 `binding_invalid`。
5. 该账号应支持单独补开或重新绑定。
6. 不影响其他账号。

如果是 `pid_missing`：

1. 只有补开该账号客户端成功后，才可以把该账号状态改为“客户端已启动 / 待登录”。
2. 其他账号状态不受影响。

如果 CDP 端口残留但 owner 不是对应 `X5Game.exe`：

1. 标记为 `binding_invalid` 或 `cdp_owner_mismatch`。
2. 不要计入 CDP 可用。
3. 不要误判为修复成功。
4. 不清空整批。
5. 允许后续单独补开该账号。

## 3.5 UI 显示要求

账号列表“状态”列显示业务状态优先。

优先级建议：

1. `login_success` / 客户端登录成功
2. `game_entered` / 已进入游戏
3. `ready` / 客户端已就绪
4. `login_failed` / 登录失败
5. `enter_game_failed` / 进入游戏失败
6. `pid_missing` / 进程缺失
7. `pid_not_x5game` / 绑定异常
8. `binding_invalid` / 绑定异常
9. `cdp_unavailable` / CDP 不可用
10. `hwnd_invalid` / 窗口失效

`restored` 不应该作为最终显示状态覆盖业务状态。

如果需要提示修复成功，可以写日志：

```text
[修复本批窗口] 单层账号-2 窗口绑定已恢复，业务状态保持：客户端登录成功。
```

## 3.6 修复统计要求

修复完成统计需要区分：

- `restored_count`
- `pid_missing_count`
- `pid_not_x5game_count`
- `binding_invalid_count`
- `hwnd_invalid_count`
- `cdp_unavailable_count`
- `unchanged_business_status_count`

不要把 `pid_not_x5game` 算入正常存活。  
不要把 `binding_invalid` 算入正常存活。  
不要因为单个异常窗口影响整批其他账号。

## 3.7 和启动恢复 / 加速总控的关系

该逻辑必须同时适用于：

1. 点击“修复本批窗口”
2. 重新打开上号器时恢复旧批次
3. 加速器总控执行前的目标窗口过滤

重新打开上号器恢复旧批次时：

- `pid` 存在但不是 `X5Game.exe` → 标记 `pid_not_x5game`
- `port` 可连接但 owner 不是对应 `X5Game.exe` → 标记 `binding_invalid`
- `pid_missing` 不删除记录
- `cdp_unavailable` 不删除记录
- 只标记异常，不清空整批
- 不覆盖业务状态为 `restored`

加速器总控执行前：

- 跳过 `pid_missing`
- 跳过 `pid_not_x5game`
- 跳过 `binding_invalid`
- 跳过 `cdp_unavailable`
- 对可控窗口继续执行，不因单个窗口失败中断全部

## 3.8 测试要求

补充测试：

1. 原状态为“客户端登录成功”，执行修复窗口后仍保持“客户端登录成功”。
2. 原状态为“已进入游戏”，执行修复窗口后仍保持“已进入游戏”。
3. `restored` 只出现在修复结果或日志，不覆盖业务状态。
4. `pid_not_x5game` 不计入正常存活。
5. `pid_not_x5game` 不会被误判为修复成功。
6. `binding_invalid` 不计入正常存活。
7. `pid_missing` 补开成功时，只影响该账号，不影响其他账号。
8. 修复一个关闭窗口时，其他已登录账号状态不变。
9. `client_direct_sessions.json` 不会因为修复动作被写成统一 `restored` 状态。
10. 重新打开上号器恢复旧批次时，也不会把业务状态统一改成 `restored`。
11. 白屏 / 卡死 / 强制关闭后的残留 pid / hwnd / cdp_port 能被识别为异常绑定。
12. 客户端直登、加速器总控、批次恢复测试继续通过。

# 五、P3：加速器导航恢复增强

## 5.1 背景

实际使用中发现一个新的稳定性问题：

用户用上号器登录账号后，X5Game 客户端没有关闭。  
如果在客户端里右键打开浏览器菜单，并点击：

```text
Back
Forward
Reload
```

可能出现以下现象：

1. 点击 `Back` 后，页面回到二维码登录界面。
2. 再点击 `Forward` 后，页面回到游戏登录界面。
3. 原网页自带加速器重新出现。
4. 我们自己的 `speed-hack-panel` 消失。
5. `timer_hook` 注入状态丢失。

原因判断：

Back / Forward / Reload 会触发页面导航或 JS 执行环境重建。  
之前通过 `Runtime.evaluate` 注入的 `timer_hook`、`speed-hack-panel`、隐藏原网页加速器脚本都属于当前页面 JS 上下文。  
页面返回 / 前进 / 刷新后，旧 JS 上下文销毁，所以自定义加速器会消失，原网页加速器会重新出现。

这类情况会经常发生，尤其是用户误点右键菜单时，所以需要增强。

---

## 5.2 修复目标

必须做到：

1. 页面 Back / Forward / Reload 后，自动重新注入自定义加速器。
2. 页面导航后，自动重新隐藏原网页展开加速面板。
3. 页面导航后，自动重新删除原网页火箭入口按钮。
4. 尽量保持用户上次设置的倍率。
5. 不需要重新登录。
6. 不需要重新准备客户端。
7. 不影响客户端直登主流程。
8. 不修改 `timer_hook` 加速核心算法。
9. 单个窗口恢复失败不能影响其他窗口。
10. 加速器总控执行时，也要具备“缺失则重注入”的能力。

---

## 5.3 推荐实现方式

### 5.3.1 使用 CDP 页面生命周期监听

对每个客户端绑定的 `cdp_port`，在可行范围内监听：

- `Page.frameNavigated`
- `Page.lifecycleEvent`
- `Runtime.executionContextCreated`
- `Runtime.executionContextDestroyed`
- `Page.loadEventFired`
- `Page.domContentEventFired`

当检测到页面导航、上下文重建、Back / Forward / Reload 后：

1. 延迟一个短时间，例如 300ms ~ 1000ms。
2. 调用现有 speed panel 注入逻辑。
3. 调用原网页加速浮层隐藏逻辑。
4. 调用火箭入口按钮隐藏 / 删除逻辑。
5. 读取或恢复上次倍率。
6. 如果当前窗口已设置过倍率，则重新执行：

```javascript
window.__H5_SPEED_APPLY__(lastRate)
```

### 5.3.2 使用 `Page.addScriptToEvaluateOnNewDocument`

如果当前 CDP 封装支持，建议使用：

```text
Page.addScriptToEvaluateOnNewDocument
```

把最小化的恢复守护脚本预注入到新文档中。

作用：

1. 新页面文档创建时就安装基础守护逻辑。
2. 比普通 `Runtime.evaluate` 更早。
3. Back / Forward / Reload 后也能自动执行。
4. 用于：
   - 隐藏原网页加速器
   - 删除火箭入口
   - 安装 contextmenu 拦截
   - 标记需要重新注入 speed panel

注意：

不要重复安装多份脚本。  
需要幂等标记，例如：

```javascript
window.__H5_SPEED_NAV_GUARD_INSTALLED__ = true
```

---

## 5.4 右键菜单处理

当前用户可以右键打开浏览器菜单，并误点 Back / Forward。

建议增加可配置项：

```text
block_browser_context_menu = true
```

默认建议：

```text
true
```

注入页面 JS：

```javascript
document.addEventListener('contextmenu', function(e) {
  e.preventDefault();
  e.stopPropagation();
  return false;
}, true);
```

要求：

1. 只在 X5Game 游戏页面内拦截右键菜单。
2. 不影响上号器自身 UI。
3. 不影响系统其它窗口。
4. 如果后续发现游戏内需要右键，可以在高级配置里关闭。
5. 右键拦截脚本也要支持 Back / Forward / Reload 后自动重新安装。

日志示例：

```text
[加速器守护] 已启用右键菜单拦截，避免误点 Back / Forward。
```

## 5.5 倍率状态保存

新增或复用配置 / 批次字段保存上次倍率：

- 全局最近倍率，例如 `last_speed_rate`
- 或每个 binding 的 `speed_rate`

建议：

1. 加速总控应用倍率时，保存到 binding 或 batch。
2. 单窗口 `speed-hack-panel` 应用倍率时，如能通过 CDP 读取，也尽量同步。
3. 页面导航后，如果检测到 `__H5_SPEED_APPLY__` 缺失，重新注入后应用上次倍率。
4. 如果没有历史倍率，默认恢复 `1.0`。

日志示例：

```text
[加速器守护] 检测到页面导航，已重新注入 speed-hack-panel，恢复倍率=50。
```

## 5.6 与加速器总控的关系

加速器总控执行时也必须具备恢复能力。

执行倍率应用前：

1. 检查目标窗口 CDP 是否可用。
2. 检查页面是否存在：

```javascript
window.__H5_SPEED_APPLY__
```

3. 如果不存在：
   - 重新注入 `timer_hook` / `speed-hack-panel`
   - 重新隐藏原网页加速器
   - 重新删除火箭入口按钮
   - 再应用倍率

总控日志示例：

```text

```

## 5.7 异常处理

如果 Back 后停留在二维码页：

2. 不要刷新页面。
3. 不要乱点二维码页。

2. 自动隐藏原网页加速器。
3. 自动删除火箭入口按钮。
4. 恢复上次倍率。

# 六、P4：新增加速器总控

## 4.1 目标

新增“加速器总控”，在上号器主界面批量控制窗口加速倍率。

典型场景：

1. 当前批次有 31 个窗口。
2. 输入倍率 50。
3. 点击“应用到当前批次”。
4. 31 个窗口全部应用 50 倍速。

本质实现：

通过每个窗口绑定的 `cdp_port` 执行 `Runtime.evaluate`：

```javascript
window.__H5_SPEED_APPLY__(rate)
```

---

## 4.2 UI 建议

在客户端直登模式区域增加：

```text
加速总控：
倍率：[1.0      ]  [应用] [恢复 1.0]
快捷：[2] [5] [50] [500]
作用范围：[当前批次 / 选中窗口 / 全部存活批次 / CDP可用窗口]
状态：成功 0 / 失败 0 / 未注入 0
```

默认倍率：`1.0`  
默认作用范围：`当前批次`

---

## 4.3 作用范围

支持：

1. 当前批次
2. 选中账号 / 选中窗口
3. 全部存活批次
4. CDP 可用窗口

默认：

```text
当前批次
```

---

## 4.4 倍率校验

倍率输入必须校验：

1. 不能为空。
2. 必须是数字。
3. 必须大于 0。
4. 支持小数，例如 1.5。
5. 支持快捷按钮：2 / 5 / 50 / 500。
6. 非法输入要提示，不要执行。
7. 不要因为输入异常导致程序崩溃。

日志示例：

```text
[加速总控] 倍率输入无效：abc
```

---

## 4.5 执行逻辑

点击应用倍率后：

1. 根据作用范围获取目标 binding。
2. 过滤掉 `pid_missing` / `cdp_unavailable` / 已关闭窗口。
3. 对每个 `cdp_port` 执行 `Runtime.evaluate`。
4. 如果页面已有：

```javascript
window.__H5_SPEED_APPLY__
```

则直接执行：

```javascript
window.__H5_SPEED_APPLY__(rate)
```

5. 如果没有 `__H5_SPEED_APPLY__`：
   - 先重新注入 `timer_hook` / `speed panel`
   - 再执行 `__H5_SPEED_APPLY__(rate)`
6. 单个窗口失败不能中断全部。
7. 汇总结果：

```text
[加速总控] 目标31，成功30，失败1，未注入0。
```

---

## 4.6 失败处理

单个窗口失败不能中断其他窗口。

失败原因需要记录：

- `pid_missing`
- `hwnd_invalid`
- `cdp_unavailable`
- `inject_failed`
- `apply_failed`
- `timeout`

日志继续脱敏，不输出 token/sign/cookie/完整 URL。

# 七、P5：关闭上号器后重新打开继续控制旧窗口

## 5.1 使用场景

必须支持这个场景：

1. 用户先用上号器客户端直登登录一批账号。
2. 登录完成后关闭上号器。
3. `X5Game.exe` 游戏窗口不关闭。
4. 用户过一会儿重新打开上号器。
5. 上号器自动加载之前保存的 `client_direct_sessions.json`。
6. 自动检测旧批次中的 `pid` / `hwnd` / `cdp_port` 是否仍然有效。
7. 对仍然存活且 CDP 可连接的窗口，恢复为可控制状态。
8. 加速器总控可以继续对这些窗口批量应用倍率。

---

## 5.2 启动恢复批次

程序启动时：

1. 从 `user_data_dir/client_direct_sessions.json` 读取历史批次。
2. 恢复 `active_batch_id` 和所有历史批次。
3. 对每个 binding 做健康检查：

- `pid` 是否存在
- `hwnd` 是否有效
- `cdp_port` 是否 connectable
- 窗口标题是否可读取
- `X5Game.exe` 进程是否仍在

4. 检查通过：
   - 状态保持或更新为“可控制 / 已连接 / 客户端存活”。
5. 检查失败：
   - 不删除记录。
   - 标记为：
     - `pid_missing`
     - `hwnd_invalid`
     - `cdp_unavailable`
     - `window_lost`

6. UI 当前批次下拉仍然显示旧批次，例如：

```text
全部-31号 | 绑定31 | 存活30 | CDP可用30 | 端口9231~9261
```

---

## 5.3 不能做的事

重新打开上号器时：

1. 不能清空旧批次。
2. 不能自动关闭旧 `X5Game`。
3. 不能要求重新登录。
4. 不能要求重新准备客户端。
5. 不能因为个别窗口失效就删除整批。
6. 不能覆盖 `client_direct_sessions.json` 为新的空文件。

---

## 5.4 重新注入要求

如果游戏页面还在，但 `timer_hook` 脚本不存在：

1. 不刷新页面。
2. 不重新登录。
3. 通过 CDP `Runtime.evaluate` 重新注入 `speed panel` / `timer_hook`。
4. 然后应用倍率。
