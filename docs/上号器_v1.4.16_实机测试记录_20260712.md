## 二、本轮发现的问题

### 1. 加速器快捷键输入方式不合格

当前界面使用一个自由文本输入框，让用户手工填写组合键。实机操作中：

- 输入或组合方式不直观；
- 只输入 `Ctrl+Shift` 时，程序提示“快捷键至少需要 Ctrl、Alt、Shift 中的一个修饰键”，提示内容和实际问题不匹配；真实缺失的是字母、数字或 F1~F12 主键；
- 日志出现“加速器快捷键已注册：Ctrl+9”，但用户实测快捷键没有产生预期的面板展开/收起效果；
- 当前不能判定为可用。

本项状态：`FAIL`。

### 2. 快捷键 UI 调整要求

后续修复时必须改为明确选择，不再让用户手输字符串：

- 修饰键 1：下拉框，选项为 `无 / Ctrl / Alt / Shift`；
- 修饰键 2：下拉框，选项为 `无 / Ctrl / Alt / Shift`；
- 主键：单独下拉框，选项为 `A~Z / 0~9 / F1~F12`；
- 两个修饰键不能重复；
- 至少选择一个修饰键和一个主键；
- 界面实时显示最终组合，例如 `Ctrl + Shift + F9`；
- 保留“应用”和“清除”；
- 注册失败、系统冲突和输入缺失必须分别给出准确提示；
- 快捷键设置不能继续放在“高级配置”内部，应移动到加速器功能区或独立的“快捷键设置”区域；
- 功能仍只允许展开/收起当前前台、精确验证 binding 的 X5Game 加速面板，不允许直接修改倍率或批量作用其他窗口。

### 3. 树形加速器的 `＋/－` 逻辑不符合需求

视频实机确认：当前左上角树形加速器把 `＋/－` 做成了固定档位跳转，代码使用 `PRESETS = [1, 2, 5, 50, 500]`，因此 `＋/－` 只会在这些预设倍率之间移动。

这不是用户要求的行为。后续修复要求：

- 不再额外增加一行“当前速率”；原来收起状态显示“速”的位置，直接动态显示当前倍率；
- 初始显示为 `1x`；只有小于 `1x` 时显示一位小数，例如 `0.9x`、`0.8x`、`0.1x`；`1x` 及以上全部显示整数，不出现 `1.0x`、`1.9x`、`2.0x`；
- 当前倍率小于 `1x` 时，点击 `＋` 每次增加 `0.1`，直到恢复为 `1x`；当前倍率达到或高于 `1x` 后，点击 `＋` 每次增加 `1`，例如 `1x → 2x → 3x`；
- 当前倍率高于 `1x` 时，点击 `－` 每次减少 `1`；当前倍率为 `1x` 时，点击 `－` 变为 `0.9x`；低于 `1x` 后继续每次减少 `0.1`；
- 最低倍率固定为 `0.1x`，到达最低值后继续点击 `－` 不再降低；
- `＋/－` 必须根据当前实际倍率做数值增减，不能再把当前倍率映射到固定档位；
- `1 / 2 / 5 / 50 / 500` 仍可作为快速预设按钮保留；
- 点击预设按钮后，原“速”位置显示的倍率必须同步更新；
- 只有底层倍率设置成功后，才更新显示、高亮和持久化值；
- 面板重新注入、刷新或导航恢复后，根标签显示必须与真实保存倍率一致。

入口触发方式追加确认：当前鼠标移动到加速器入口就显示面板，后续只改为点击入口后显示；单纯悬停不得触发。除这一点外，面板位置、拖动能力、鼠标移出后的隐藏行为、关闭方式和其他交互全部保持现状，不在本轮顺带调整。

本项状态：`FAIL`。

### 4. “执行客户端登录”仍受“自动进入游戏”复选框控制

本轮实机确认：用户未勾选“自动进入游戏”时，点击“一键准备并登录”会按预期停在公告/进入游戏前，这一阶段行为正确；但窗口排列完成后，再手动点击“执行客户端登录”，仍然不会进入游戏。

代码确认根因：`_start_client_direct_prepared_login_run()` 会再次读取 `_client_direct_auto_enter_game()`，并把当前复选框状态传给登录 worker。因此复选框未勾选时，手动“执行客户端登录”也被强制按“不自动进入游戏”执行，最终只显示“客户端已就绪”。

后续修复要求：

- “自动进入游戏”复选框只控制“一键准备并登录”的自动连续流程；
- 未勾选时，“一键准备并登录”可以准备、排列并停在公告/进入游戏前；
- 用户随后主动点击“执行客户端登录”属于明确的人工继续操作，此时应直接调用进入游戏流程，不再受该复选框限制；
- 为避免歧义，按钮文案建议调整为“执行登录并进入游戏”或同等明确文案；
- 手动执行前仍必须保留现有 HWND、PID、CDP 归属复核；
- 进入失败必须记录真实失败原因，不能仅显示“已就绪”。

本项状态：`FAIL`。

### 5. “旧方式二（高级）”并未删除，只是隐藏，且会污染当前模式

本轮实机确认：在客户端直登模式下展开高级配置后，“旧方式二（高级）”入口重新出现。点击该入口后，程序真实切换到旧方式二账号密码模式，显示“上号方式”“CSV 文件”“CSV 账号列表（方式二）”等旧界面；随后“分组设置”提示“全部串行分组设置仅用于方式一收藏夹账号”。日志也在“旧方式二（高级）”与“客户端直登模式”之间反复切换。

这说明旧方式二并不是已删除功能，而是按钮、`method2` 状态、CSV UI、运行分发和账号来源切换仍完整存在，只是平时隐藏。高级配置展开又会把入口重新显示，导致隐藏功能重新参与运行状态。

后续修复要求：

- 彻底删除“旧方式二（高级）”和“旧方式二账号密码”入口，不允许继续用 `pack_forget/grid_remove` 隐藏代替删除；
- 删除旧方式二 CSV 文件选择、导入、CSV 账号表格和旧运行按钮；
- 删除 `method2` 模式切换、旧方式二单账号/全部运行分发及无调用方执行代码；
- 展开或隐藏高级配置不得改变工作模式、账号来源、当前账号列表和分组设置；
- 客户端直登模式下“分组设置”必须继续正常用于刷新地址第 4 个参数动态生成的分组，并只控制选择“全部”时哪些分组参与运行；
- 历史配置若保存为旧方式二，启动时迁移到客户端直登模式，不得恢复已删除入口；
- 不删除用户磁盘上的 CSV 或账号数据文件，只移除程序中的旧功能实现和入口。

本项状态：`FAIL`。

### 6. “旧版兼容模式”已无用途，应彻底删除

本轮实机确认：客户端直登模式下展开高级配置后，除了“旧方式二（高级）”，还会重新显示“旧版兼容模式”。

用户已确认：该流程已被客户端直登模式完全替代，不再作为兜底能力保留。因此不能继续隐藏，必须删除完整旧功能链。

后续要求：

- 彻底删除“旧版兼容模式”按钮和 `RUN_MODE_FOREGROUND_LABEL`；
- 删除相关模式映射、切换回调、前台辅助/OCR 上号分发及无调用方执行代码；
- 删除高级配置控制工作模式按钮显示的耦合；
- 展开或隐藏高级配置不得改变当前模式、账号来源、分组设置和账号列表；
- 历史配置若保存为旧版兼容/前台辅助模式，启动时自动迁移为客户端直登模式；

## 三、高级配置审计结论

代码中的“高级配置”当前包含：收藏文件路径、`bookmark_root_path`、兼容目录名、自动化设置路径、每层数量、默认端口起点、加速面板固定选项和加速器快捷键。

经本轮逐项确认，处理完成后没有任何内容需要继续留在独立“高级配置”区域，因此决定删除整套“显示/隐藏高级配置”按钮和面板。

处理方式：

- `手动选择 Bookmarks`：不再保留。普通 UI 不再显示自动/手动路径选择、收藏候选和账号目录等技术过程控件；收藏夹文件只在写回地址时后台自动定位，账号来源和分组不再依赖收藏夹扫描；
- `bookmark_root_path`、兼容目录名：后台收藏夹写回和兼容迁移使用，普通 UI 不显示；
- `automation_settings.json`：文件本身继续作为核心配置自动读写，但删除“自动化设置路径”输入框和选择按钮；
- `每层数量`：UI 和固定数量限制删除，改为按刷新地址账号库及第 4 个参数动态统计分组和账号数；
- 默认端口起点：后台保留，普通 UI 不显示，程序继续自动寻找连续可用端口；
- 加速面板选项：全部改为内部固定行为，不再显示；
- 原浮层诊断日志：仅开发者诊断使用；
- 加速器快捷键：移动到独立快捷键区域；
- 高级配置删除后，不得再有任何展开逻辑影响工作模式、账号来源、分组设置或账号列表。

本项状态：`CONFIRMED_FOR_REMOVAL`。

## 四、统一账号管理设计确认

用户确认不再需要手动选择 Bookmarks。现有“读取收藏夹 / 账号配置”区域应简化为：

```text
账号配置    [账号管理]
```

“账号管理”只展示“刷新地址”账号库中的账号，并管理登录顺序、上号参与状态和链接状态。收藏夹不再作为账号管理的独立账号来源，不向账号管理列表补账号，也不决定账号是否存在；刷新地址账号记录中的第 4 个参数 `bookmark_path` 用于自动识别分组和收藏夹写回。

弹窗至少包含：

1. 登录顺序；
2. 名称；
3. 分组；
4. 收藏夹路径；
5. 直登状态；
6. 直登链接（界面脱敏显示，底层保留完整链接）；
7. 上号状态。

功能要求：

- 支持全部、已参与、未参与、链接缺失、链接过期和按分组筛选；
- 支持上移、下移，保存后真实影响下一次客户端准备、槽位分配和登录顺序；
- 账号管理的账号范围只以“刷新地址”账号库为准，不再从收藏夹或本地直登链接库单独拼接账号；
- 主界面的分组下拉框、账号下拉框和“分组设置”继续保留，分组选项和数量由刷新地址账号库动态生成；
- 选择具体分组时，只运行该组中账号管理状态为“已参与”的账号；即使该组未勾选参与“全部”，仍可单独运行；
- 选择“全部”时，只运行“分组设置”中已勾选的分组，再过滤账号管理中“已参与”的账号，并保持全局相对顺序；
- “分组设置”只控制“全部”包含哪些组，账号管理只控制单个账号是否参与，两者职责分离；
- 保留实机既有工作流：桌面 1 选择“单层账号”运行 9 个账号；桌面 2 选择“全部”只运行第一层至第四层等已勾选分组共 31 个账号，不重复运行刚登录的 9 个单层账号；
- 第 4 个参数为空的账号归入“默认组”；默认组首次出现时默认参与“全部”，之后允许在“分组设置”中取消；空路径账号正常刷新本地直登链接，但不执行收藏夹写回；
- `账号/1`、`账号/A1`、`账号/张三` 等直接位于账号根目录的路径归入逻辑分组“单层账号”；
- `账号/第一层/1`、`账号/第一层/A1`、`账号/存钻/测试号` 等路径取最终收藏项的上一级目录作为分组；
- 收藏项名称允许数字、字母、中文及组合形式，不再限制纯数字；初次排序使用刷新地址导入顺序，后续使用账号管理顺序，窗口号不再由收藏项名称决定；
- 账号管理只提供“从上号列表移除”，不提供容易与刷新地址破坏性删除混淆的“移除账号”；该操作只把账号改为“未参与”，不删除刷新地址中的账号、凭据、直登链接或生成 URL 文件；
- 刷新地址中仍有该账号时，账号管理移除后继续显示为“未参与”；后续执行“刷新选中”或“刷新全部”只更新链接状态，不自动重新加入上号列表，也不改变登录顺序；
- 刷新地址中已移除该账号时，账号管理暂不即时变化；未执行刷新地址操作前保持原样，下一次执行任意刷新地址操作并完成账号库对账后，该账号必须从账号管理中消失，并清理参与状态和排序残留；
- 后续重新导入或新增到刷新地址后，下一次对账时重新出现在账号管理中，默认“未参与”，可再手动加入上号列表；
- 排序和是否参与上号使用独立登录清单保存，不复用刷新账号的 `enabled` 字段；
- 使用稳定账号标识保存关系，不能只依赖可能改名的显示名称；
- 必须兼容默认组、单层账号、分组数量不固定、第一层 10 个以上账号、自定义分组、字母或中文收藏项、同名账号、收藏夹路径移动或缺失、直登链接缺失或过期等情况。

当前“刷新地址”弹窗中的“删除账号”会移除本地刷新账号记录、直登链接记录、生成的 `.url`、批次绑定和运行缓存，但不会删除用户原始 CSV/Excel/文本导入文件，也不会删除浏览器收藏夹。新账号管理弹窗不得调用该删除逻辑。刷新地址中的按钮统一改名为“移除账号”，确认框必须明确说明只移除上号器内部保存的数据和关联资源，不会删除客户原始导入文件或浏览器收藏夹。

收藏夹写回规则新增确认：刷新地址账号保存目标收藏夹路径。账号直登地址刷新成功后，目标路径唯一存在时更新原收藏项 URL；目标路径不存在时，自动创建缺失的文件夹层级和账号收藏项并写入新 URL，实现“有则更新、无则新增”。收藏项名称允许数字、字母、中文及组合形式；路径为空时只刷新本地直登链接，不执行收藏夹写回。存在多个同名路径时禁止盲目写入并提示冲突；浏览器运行中继续按安全规则暂不改写 Bookmarks。该收藏夹写回不会改变账号管理中的参与状态和登录顺序。

## 二十、v1.4.17 实机复验失败：Back/Forward 生命周期仍未恢复（2026-07-12）

- 当前守护仍属于“注入到页面内部的 JavaScript 自守护”，依赖当前 document 中的 `pageshow/popstate/load/MutationObserver`；
- 登录完成后 `execute_prepared_client_direct_login()` 在 `finally` 中关闭 CDP 连接；
- 页面被历史导航销毁、换成新 document、恢复到不同 target，或 X5 对 DevTools 会话状态进行重置后，旧页面脚本无法从外部重新注入自己；
- `Page.addScriptToEvaluateOnNewDocument` 只在登录阶段通过当时的 CDP 会话注册，真实 X5 历史导航后不能假定该注册仍持续生效；
- 当前自动化用例主要检查生成脚本中存在 `pageshow/popstate/MutationObserver` 字符串，并没有构造真实 X5Game、真实 CDP 会话断开和 Back/Forward target 切换，因此自动化通过不代表此项实机通过。

下一步修复方向：

- 不再只继续叠加页面内事件监听；
- 增加宿主侧长期生命周期守护，在 X5Game 存活期间持续或可重连地管理对应 CDP endpoint；
- 监听或轮询 target/document 变化，发现新的 page target、execution context 或面板缺失时，重新执行面板注入、原生入口抑制和倍率恢复；
- 倍率以 binding/批次保存的真实 `speed_rate` 为宿主侧权威值，重新注入后恢复该值，不能只依赖当前页面 localStorage；
- 守护必须支持 9/31 窗，不得为每个窗口创建失控的重复线程、重复 WebSocket、重复 hook 或重复面板；
- 保留 v1.4.15 误收起保护和 `TIMER_HOOK_SCRIPT` 核心算法不变。

状态：`KNOWN_LIMITATION_ACCEPTED_USE_REPAIR_BATCH_WORKAROUND`。用户决定不再开发常驻宿主侧生命周期守护，以避免给后续总工程增加线程、CDP 连接、句柄和内存开销。Back/Forward 后若自定义加速器消失、原生入口重新出现，执行现有“修复本批窗口”重新完成 CDP 校验与加速器注入。本项不再阻塞收尾，不升 v1.4.18，未打包正式 EXE。

## 二十三、v1.4.18 实机阻塞：刷新地址后 Edge 收藏夹整套重复（2026-07-12）

实机过程：

- 32 位源码环境因缺少 `requests`，纯 HTTP 刷新失败并自动回退 Playwright；用户中途停止，但停止前已有前若干账号完成收藏夹写回；

- 刷新后 Edge 收藏夹出现大量成对重复，不仅包括本轮命名账号，也包括旧数字收藏项 `1/2/3/...`；截图中多个账号连续出现两份；

- `Bookmarks_Edge_Default_20260712_172302_602736.json` 是 17:23 本轮第一次写入前创建的自动备份；其中 `幻域乄灵渊` 等前序账号只有一份；
- 该备份中的旧数字收藏项带 `source=sync`，本轮刷新日志并未处理数字路径；因此数字项成对出现不能由“同一账号刷新循环执行两次”解释；
- 当前收藏夹写回实现会直接读取并原子替换 Edge `Bookmarks` 文件，每个账号成功后都会独立写一次；仅检查 Edge 进程是否运行，没有处理 Edge 收藏夹同步、`Bookmarks.bak` 恢复或启动后的云端合并；
- 32 位和 64 位调用的是同一套 `BookmarkUrlUpdater`，位数只影响依赖是否可用以及 HTTP/Playwright 路径，不会直接导致收藏夹节点复制。

当前判断：

- 用户确认以前版本执行同类刷新没有发生重复，因此本问题应优先按“近期收藏夹写回回归”调查，不能简单归因于 Edge 一直存在的同步问题；
- 文档和测试表明，早期行为是路径不存在时返回 `bookmark_not_found`，当前实现新增了“路径不存在时自动创建最终收藏项/中间目录”；与此同时当前刷新仍是每成功一个账号就完整替换一次 `Bookmarks` 文件；
- 当前自动化只验证临时 JSON 中自动创建、校验和及原子替换成功，没有覆盖 Edge 重启、收藏夹同步、`Bookmarks.bak` 恢复和云端合并后的真实结果；
- 更高概率的回归链是：某次路径匹配未命中 → 当前版本自动新增节点 → 多账号重复整文件写回 → Edge 同步/恢复将原有集合重新合并，从而出现成对重复；Edge 同步可能是放大因素，但最近新增的自动创建与逐账号整文件写回是首要可疑变化；

- 在读取当前实际 `Bookmarks`、`Bookmarks.bak`、同步状态和重复节点 GUID/父目录前，不能把上述回归链写成最终确定根因。

1. 刷新开始前完成收藏夹同步/浏览器状态预检；状态无法确认时只刷新本地直登链接，不直接写真实 Bookmarks；

5. 写入后重新读取文件并验证每个目标路径严格唯一；必要时在浏览器重新打开后再做一次实机确认；

7. 缺少 `requests` 属于环境依赖错误，不得自动回退并突然打开浏览器，应在批量开始前提示并阻止或由用户明确选择 Playwright。
